# P1-6: release qualification and user-facing documentation

The owner authorized this step with "P1-6 开始". The approved P0-4 sequence calls for source/wheel qualification, installed workflows, the selected platform matrix and truthful user documentation. P1-5 PR #5 was open and unmerged at the start; its verified head is `e1eb904a5e2e00fa5c5f0ffbf29502d2c920a55a`. This step uses branch `phase1/p1-6-release-qualification` and candidate version `0.1.0rc1`.

## Delivered scope

- A practical README first-run path and [USER_GUIDE.md](USER_GUIDE.md) for preparing records, selecting scope/requests, interpreting conditions and handling failures without treating synthetic receipts as real evidence.
- A small clean-commit candidate builder using the existing setuptools backend. It verifies exported paths, file modes and blob identities against the committed tree, stamps only its copy, builds the sdist and then its wheel, verifies identity preservation, and emits actual artifact hashes. Dirty sources, wrong revisions, inconsistent versions, attribute-driven source omissions/substitutions, unsafe archive layouts and existing destinations are rejected.
- Package-embedded build identity as `ect-VERSION+git.SOURCE_REVISION`. Ordinary source builds remain explicitly unknown. The analyzer reads a static constant, without runtime Git, environment or filesystem provenance lookup.
- Installed-package checks against an independently supplied expected build ID, package/license metadata and bytes, x64 identity, and actual README/user-guide/reproducibility examples.
- Four-cell CI on the exact source commit, tests from extracted sdist source against the installed wheel, and retained candidate artifacts. Feature branches are checked on PRs; main pushes retain qualification, avoiding duplicate branch-push and PR runs.

The dossier schema, method/policy, mathematical calculations, evidence qualifications, request operations and public API surface are unchanged. The report's build ID uses its existing field. Global limitation wording now applies accurately to both source and stamped builds and distinguishes software qualification from empirical effectiveness. Report digests therefore change with version/identity/wording as expected. The prior fourteen demos' analytical results and findings are compared with P1-5 before refreshing normalized parity hashes.

## Distinct verification responsibilities

| Responsibility | Verification |
| --- | --- |
| Semantic behavior and safe delivery | Existing direct regression suite, literal examples and counterexamples |
| Source/build identity | Exact clean HEAD, static exported stamp, identity preserved through sdist/wheel, independent installed expectation |
| Distribution completeness | Extracted-sdist tests, packaged schema/demos, metadata/license, zero runtime dependencies |
| First-use documentation | Actual marked README examples, user-guide examples and reproducibility snippets run from the installed wheel outside the checkout |
| Platform claim | CPython 3.12/3.13 on Ubuntu 22.04 x64 and Windows Server 2022 x64, with actual job outcomes recorded on the PR |

Focused builder tests cover boundary failures; they do not replay project history or reproduce the predecessor CI matrices. Real candidate builds run locally and in this project's selected cells. Artifact hashes describe the bytes produced, without claiming reproducible packaging, a signed supply-chain attestation or authenticated evidence. All supplied demos remain synthetic.

## Acceptance stop

The [release procedure](RELEASE.md) records the maintainer commands and remaining owner decisions. Actual test totals, exact candidate commit, artifact hashes and four-cell outcomes are recorded on the P1-6 PR after verification. The candidate code and docs can be accepted when those checks pass with no unresolved blocker for the declared scope.

This step stops at the reviewable candidate PR. It does not merge earlier PRs, create tags, publish a GitHub Release or package-index distribution, or claim that stable `0.1.0` has been released. A later authorized stable-version or merge commit must be rebuilt and qualified in its own identity. Capture/replay, simulation, adapters, live collection and empirical effectiveness studies remain outside this stage.
