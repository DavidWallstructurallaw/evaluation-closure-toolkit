## 3. P0-4 clarification incorporated into P0-3

The bounded readiness review found one initial-lint output ambiguity. P0-3 admitted `lint` for an `open_evaluation` claim, but its explicit lint conclusion rule initially covered only `narrow_regression`. P0-3 now states:

- Open-claim lint does not execute five-condition assessment.
- A decisive scoped contradiction may yield `defeated_under_scope`.
- Otherwise performed open-claim lint yields `unestablished`, including when every disclosure is complete.
- Unperformed lint yields `not_assessed`.
- Open-evaluation `supported_under_scope` is available only from the separately implemented `assess` operation.

This preserves the distinction between disclosure review and the five-condition assessment. It remains true after P1-4 implements assess. A P1-1 acceptance fixture must cover a fully disclosed open claim and verify that lint never awards five-condition support.

The same document update escapes literal enum separators inside Markdown tables so the contracts render as intended. It changes no enum values, wire fields, formulas or selected scope. P0-3's earlier version remains historical; its corrected version is the implementation input identified in section 7.

## 4. Selected v0.1 boundary

The accepted design candidate remains one local JSON dossier, strict admission, scoped evidence findings and JSON/Markdown reports. Initial implementation uses Python with no third-party runtime dependency. The supported target capabilities are:

1. Claim/reporting lint, including scope, evidence-type and currentness distinctions.
2. Hard-assignment structural accounting, compatible descriptive snapshots and explicit matched cohorts.
3. Typed lineage witnesses and member-scoped external contact/use qualification.
4. Anomaly/revision traceability, correction evidence and five-condition assessment.
5. Installed synthetic demos and deterministic rerun documentation.

The arithmetic and findings remain conditional on supplied records and reviews. There is no universal openness, integrity, truth or collapse score, no automatic semantic classifier, no hidden-ancestry discovery and no deployment authorization.

Simulation stays with the optional RIT companion workflow. Capture archives, a replay command, cross-tool adapters, shared frameworks, soft/multilabel assignment, benchmark execution and live data collection remain outside this release.

The proposed four qualification cells are CPython 3.12/3.13 on Ubuntu 22.04 x64 and Windows Server 2022 x64. They are test targets. Compatibility will be claimed only after this project's installed workflows pass there. Runtime/build configuration, machine-readable schema construction and executable fixtures are implementation work, not missing P0 evidence.

## 5. Concrete P1-1 work ready to authorize

**Delivery:** an installable package that accepts a caller-prepared dossier and produces a useful claim-lint report, even when semantic evidence is incomplete.

The step includes:

- Bring the approved Phase 0 contracts into the repository as engineering documentation, excluding theory PDFs and private input material. Use the corrected P0-3 baseline and this decision. Preserve the initial license and repository identity.
- Implement strict bounded UTF-8/JSON admission, the complete closed record/reference grammar, and explicit missing semantic facts. Admission of a later operation's input does not imply its analysis is implemented.
- Implement the fixed `lint` rules and their evidence/currentness/scope boundaries, including the open-claim clarification above.
- Provide `validate`, `analyze`, and `demo`, with `validate_bytes`, `analyze_bytes`, and `render_markdown`.
- Provide authoritative JSON and equivalent safe Markdown, deterministic identities and the specified exit behavior.
- Ship real synthetic incomplete-regression, supported-narrow-regression, and scope-mismatch fixtures, plus the open-claim lint boundary case. These are runnable installed examples, with independent expected outcomes.
- Add focused semantic, admission, I/O and installed-package verification. Present the implementation on a reviewable feature branch/PR before later merge or release decisions.

Selected but unimplemented operations must return `not_run`, `unsupported_operation`, EC108 and exit 3. They cannot return an empty success report or fabricated scientific findings. No empty future module tree or placeholder analytical implementation is required.
